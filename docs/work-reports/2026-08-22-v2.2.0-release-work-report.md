## 前次 Empty reply 根因与修复

前次失败请求的 curl exit code 为 52、HTTP status 0/null、response bytes 0、总时长约 3 秒。curl remote socket 明确为 `127.0.0.1:7890`，宿主存在 `HTTPS_PROXY=http://127.0.0.1:7890` 且 `NO_PROXY` 未包含 Production endpoint；Edge/Frontend 为 499，Backend 随后正常完成 HTTP 200，Java HTTP 200 且 fallback=false。因此响应丢失发生在 acceptance client 到本机代理的路径，不是应用代码。

修复后的 Production collector：

- 安全解析 Production HTTPS hostname/port；
- 对每个 Production 请求移除大小写 `HTTP_PROXY`、`HTTPS_PROXY`、`ALL_PROXY`、`NO_PROXY`，并设置精确 `--noproxy <host>`；
- 明确绑定 reviewed physical interface `eth0`，避免 Mihomo transparent TUN `Meta` 路由；
- 在登录/Analyze 前运行 `/api/health` 与 `/api/ready` direct probe；
- hard assert resolved destination、remote port、TLS、local source、source-specific route 与 physical interface；
- 任意 loopback/TUN/proxy socket、路径证据缺失或不一致均立即 HARD FAIL，不会 fallback 到 proxy；
- 保留 curl exit/stderr、status/bytes、connect/start-transfer/total、local/remote socket，以及 Edge/Frontend/Backend/Java 关联证据，不记录 Resume/JD 正文、cookie、token 或密钥。

仅使用 `--noproxy` 的诊断仍显示 local `198.18.0.1`、route `Meta`，并再次产生约 3 秒 Empty reply；因此 gate 进一步要求物理 source/interface。绑定 `eth0` 后 local socket 为 `10.0.0.4`、route 为 `eth0 via 10.0.0.1`。
