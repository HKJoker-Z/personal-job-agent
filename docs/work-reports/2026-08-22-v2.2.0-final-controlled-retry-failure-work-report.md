## Reproducible public response failure

- X-Request-ID：`v220fpg-analyze1-9164ccd2ccb4`
- Start：`2026-08-22T13:08:28.417Z`
- curl exit code：52
- curl stderr：`curl: (52) Empty reply from server`
- Public HTTP status：0/null
- Response bytes：0
- Connect time：0.161 ms
- Start-transfer / total：3000.797 / 3000.811 ms
- curl remote socket：`127.0.0.1:7890`
- Host acceptance environment 明确配置 `HTTPS_PROXY=http://127.0.0.1:7890`，而 `NO_PROXY` 包含 loopback 但不包含 Production public IP；proxy URL 不含 credentials。该配置与 curl remote socket 完全一致。
- Edge：status 499，upstream status `-`，request 2497 ms，upstream response 2487 ms，bytes sent 0。
- Frontend：status 499，upstream status `-`，request/upstream response 2487 ms，bytes sent 0。
- Java：HTTP 200；collector observation 23.059 ms；Java processing log 9 ms / request total 10 ms；fallback=false。
- Backend：请求继续执行，DeepSeek latency 10003.002 ms，Analyze total 11235.569 ms，history/idempotency finalized=true，最终 `http_request_completed` status 200、duration 11329.422 ms。
- Edge/Frontend 499 发生在 Backend 完成之前约 8.9 秒。证据表明 client 所连接的 loopback proxy 在固定约 3 秒关闭，然后关闭沿 Edge/Frontend 传播；Backend 与 Java 没有提前失败。
- 容器在 failure 前后 ID、IP、health、restart/OOM 不变；Docker events 和 Nginx startup/reload windows 已保存。

这次证据将 response loss 定位到 acceptance client / `127.0.0.1:7890` loopback proxy hop。该结论是根据 curl remote socket、固定 3 秒关闭、双层 499/0 bytes 和 Backend 后续 200 作出的链路推断；下一步应专门修复/绕开并从独立外部 vantage 验证该 proxy path，而不是调整 Java timeout 或继续发布重试。
