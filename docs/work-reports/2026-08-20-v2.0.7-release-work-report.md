## Production deployment

The established production Compose project and its exact nine-file override
order were used. Preflight was GO: public Version 2.0.6 and readiness were
healthy; Backend and Java were healthy with zero restarts and no OOM; the tag,
Release, source, image digests, Java mode, and schema matched; available root
disk was 6,953,517,056 bytes and available memory was 2,417,655,808 bytes.

A protected rollback snapshot was created at:

`/var/backups/personal-job-agent-v2/v2.0.6-pre-v2.0.7-20260820T133608Z`

The rendered candidate changed only the Backend digest, Frontend digest, and
`APP_VERSION=2.0.7`. No migration command was run. PostgreSQL, Redis, Java,
Edge, networks, ports, volumes, and secrets were not changed or recreated.

The ordered cutover started with Worker and Outbox. Worker became healthy on
the v2.0.7 digest. Outbox did not: its existing healthcheck repeatedly exceeded
the configured 5-second timeout. A bounded manual execution completed
successfully only after approximately 8.3 seconds. The Outbox container became
`unhealthy`, so the hard health gate failed before Backend or Frontend was
switched.

The deployment was immediately stopped. The protected v2.0.6 Compose file was
restored byte-for-byte and Worker/Outbox were recreated on their original
v2.0.6 digest. Backend, Frontend, and Edge never left v2.0.6. No rollback
migration or data operation was needed.

complete within its configured five-second timeout under the current
production CPU limit, so v2.0.7 cannot meet the required all-application-health
acceptance gate. Production also remains on v2.0.6; therefore authenticated
production History View verification is outstanding.

Do not force the deployment, change the published tag, or move the Release.
Handle the Outbox healthcheck/runtime condition as a separately reviewed task,
then rerun the complete v2.0.7 production preflight and cutover using the
already published immutable artifacts.
