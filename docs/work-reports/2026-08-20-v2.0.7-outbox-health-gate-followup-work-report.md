# Version 2.0.7 Outbox Health Gate Follow-up Work Report

Date: 2026-08-20

Status: **COMPLETED.** The health gate configuration was corrected without
changing the Version 2.0.7 release source or images, and Version 2.0.7 was
successfully deployed to production.

## Root cause

The Outbox healthcheck itself was succeeding when allowed to finish, but the
production Compose timeout terminated it after five seconds. Under the
established `0.25` CPU limit, six baseline executions took 5.387–8.091 seconds.
Phase measurements showed that Python startup and imports consumed
3.708–5.799 seconds, while configuration loading took about 0.001 seconds,
PostgreSQL took 0.720–0.812 seconds, and Redis took about 0.071 seconds.

The check semantics are appropriate: require a heartbeat no older than 30
seconds, execute PostgreSQL `SELECT 1`, and require Redis `PING`. Dispatcher
heartbeats remained 0–1 seconds old, PostgreSQL and Redis succeeded, the
dispatcher process remained running, and the aggregate Outbox status query
showed no queued events. There was no evidence of an Outbox runtime failure.
The failure was a timeout mismatch under the production CPU limit.

## Healthcheck ownership and location

- Canonical healthcheck implementation in the immutable Backend image:
  `backend/app/agent_runs/dispatcher_healthcheck.py`.
- Canonical production policy and timeout:
  `deploy/production/compose.yaml`, service `outbox-dispatcher`.
- Live production policy:
  `/opt/personal-job-agent-v2/compose.yaml` in Compose project
  `personal-job-agent-v2`.
- The established live deployment currently invokes the equivalent protected
  bind-mounted script `/opt/pja/outbox-healthcheck.py`.
- CPU ownership remains the live Compose service limit of `0.25` CPU. It was
  not changed.

The healthcheck meaning belongs to application code; the outer execution
budget belongs to production deployment configuration. Only the latter needed
adjustment.

## Fix

- Changed only the production Outbox healthcheck timeout from 5 seconds to 15
  seconds.
- Added a production Compose render regression assertion for the 15-second
  timeout.
- Applied the same policy to the live Compose file while retaining the
  original five-second configuration in the protected rollback snapshot.

No application code, image content, dependency, schema, migration, CPU limit,
healthcheck command, heartbeat threshold, PostgreSQL check, Redis check, tag,
or GitHub Release was changed. The health gate was not disabled or bypassed.
