## 9. Hard rollback conditions

If a later deployment is authorized after the capacity issue is resolved, the
existing hard rollback conditions remain: incorrect public version or image
digest, unhealthy Backend/Frontend/Edge/Java/Worker/Outbox, authentication or
CSRF/Origin regression, Resume or History regression, public serialization
failure, deadline or Provider-call-limit breach, broken completed idempotency
replay, duplicate persistence, schema mismatch, severe secret/security
leakage, restart loop, OOM, or an untrustworthy rollback path. A partial,
fallback, Provider timeout, Provider protocol error, 429/5xx, or lower
Provider-quality percentage is not alone a rollback condition when bounded
deterministic fallback remains safe.
