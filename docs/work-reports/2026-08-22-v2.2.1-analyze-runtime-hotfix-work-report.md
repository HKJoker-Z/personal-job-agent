## 原始故障

- v2.2.0 production cutover 验收时，Public Edge 返回 `Empty reply from server`。
- 同次请求的 Backend 最终完成 Analyze 并记录 HTTP 200；Java normalize 总请求约 `3041 ms`，其中 normalizer 工作约 `133 ms`。
- Backend 在约 `607 ms` 触发当前 `response_timeout`，随后按设计使用 local fallback；release 已回滚，生产保持 v2.1.0。
- 原始事件没有留下足以定位 Edge 首次断开位置的完整关联 access/error log，因此不能从历史证据断言具体断开层。

## v2.1.0 / v2.2.0 对比

- Analyze normalization client/runtime、Frontend/production/Edge Nginx 配置和 Java request filter 在两个 tag 间 byte-identical；相关 Backend config 唯一差异是默认版本号 `2.1.0 → 2.2.0`。
- 使用同一输入及 production-equivalent Java 配置测试 immutable v2.1.0 Backend：Direct Backend、Frontend、Edge、HTTPS 均 HTTP 200；耗时分别为 `200.629 / 194.633 / 186.122 / 78.427 ms`。
- v2.1.0 的四次 Java client 耗时 `12.217 / 6.973 / 9.404 / 8.214 ms`，全部 `fallback=false`；代理关联日志无异常。
- 没有证据表明 Analyze / Java normalization 行为由 v2.2.0 Applications 变更引入。

## 最终根因与修改内容

- 最符合现有证据的分类是一次不可复现的 Java 容器/JVM/主机调度或网络路径延迟尖峰：原事件 Java 总请求 `3041 ms`，但 normalizer 自身仅约 `133 ms`。保留日志不足以进一步证明具体机制。
- 当前无法复现稳定 Java 性能问题、Backend response 传输问题或 Nginx/Edge 配置缺陷，因此没有修改应用代码、Java timeout、Nginx、Docker、dependency、schema 或 Alembic。
- 本分支只新增本诊断报告及工作报告索引。保持已有 fallback、observability 和 failure handling 不变，是证据支持下的最小方案；不为一次瞬时事件制造无依据的 v2.2.1 行为变更。
