# Version 2.1.0 — Applications

Version 2.1.0 adds a focused Applications workflow for recording jobs that the
user has actually submitted. It does not automate submission or add status,
interview, offer, search, filter, edit, or delete workflows.

## User-facing changes

- Adds Applications to the primary navigation, with an Applied Time-descending
  list and full record detail.
- Supports manual records with required Company Name and Job Title and optional
  Job Description and Resume.
- Adds an Applied action to completed Analysis results. A successful action
  creates an additional Application without moving or deleting its History
  record, shows a clear success state, and prevents repeated submission from
  the current Analysis.
- Stores the actual Resume text used by an Analysis as a snapshot so a later
  Resume edit cannot change the recorded submission context.

## Database and API

- Alembic `20260820_08` follows `20260730_07`, makes the historical
  `applications.job_id` optional, and adds submission snapshot fields plus a
  per-user unique source-Analysis constraint.
- `GET /api/applications` lists submissions newest first.
- `GET /api/applications/{application_id}` returns full detail.
- `POST /api/applications` creates a manual submission; Applied Time is always
  generated by the backend.
- `POST /api/applications/from-analysis` creates the Analysis-linked record and
  returns HTTP 409 when that Analysis was already marked Applied.

## Validation and deployment

Release validation uses deterministic/mock provider paths and includes Backend,
Frontend, Docker/Compose, production-runtime, Alembic, PostgreSQL 16 strict
backup/restore, and isolated product smoke gates. Production promotion requires
a verified PostgreSQL 16 backup before migration, an isolated candidate, exact
immutable application image digests, and Alembic `20260820_08` after cutover.

Rollback restores the Version 2.0.7 application images and protected
configuration. Because Version 2.1.0 writes new Application records, a database
rollback is an explicit incident decision using the verified pre-release backup;
the release process must not delete or silently downgrade production data.
